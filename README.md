# B+ Tree Implementation and Performance Comparison

This project is for my DBMS assignment. I implemented three B+ Tree storage approaches and compared how they behave when inserting and searching records from the supplied CSV dataset.

## Contents

| File | Description |
|---|---|
| `bplus_tree.cpp` | C++17 source code, with comments and sections for the main operations. |
| `benchmark_results.csv` | Results file generated by the program. Check which run it belongs to before using its values in the final report. |
| `report_template.md` | A simple structure for writing up the experiment. |

The official dataset should be named `bplus_tree_data_10m.csv` and placed in the same folder as the program, or its path can be supplied when running the executable.

## What I implemented

The program compares these three versions:

1. **Memory-only B+ Tree** — keeps the tree nodes and records in memory. This gives a useful baseline because the program does not need to read or write tree pages to disk.
2. **Disk-only B+ Tree** — stores tree pages in a file and uses a one-page LRU cache.
3. **Memory + Disk B+ Tree** — stores the pages on disk and uses a 256-page LRU buffer pool to keep recently used pages in memory.

The implementation includes key insertion, node splitting, linked leaf pages, exact-key search, and checks that the returned payload matches the expected value. The benchmark records insertion time, average successful search time, tree page/node count, reported storage size, tree height, disk page reads/writes, and cache hits.

## Requirements

- Windows with VS Code or another terminal
- MinGW-w64 / GCC with C++17 support
- Enough free disk space for the page files
- The supplied `bplus_tree_data_10m.csv` file for the full experiment

Check that GCC is available by running:

```powershell
g++ --version
```

## Compile the program

Open the project folder in VS Code and select **Terminal → New Terminal**. Run:

```powershell
g++ -std=c++17 -O2 -Wall -Wextra bplus_tree.cpp -o bplus_tree.exe
```

If the command finishes without a compiler error, the executable should be created in the current folder.

## Run the program

First, copy `bplus_tree_data_10m.csv` into the project folder. It should have the columns `key,payload`, as shown in the assignment dataset.

It is a good idea to try a smaller run before processing all 10 million records:

```powershell
.\bplus_tree.exe bplus_tree_data_10m.csv 10000
```

If the small run finishes and the search checks pass, run the full dataset:

```powershell
.\bplus_tree.exe bplus_tree_data_10m.csv
```

The optional second argument limits the number of records processed, which is useful for a quick test. Without that argument, the program processes the full input file.

### Files created by a run

- `benchmark_results.csv` — benchmark results from that run
- `bpt_disk_only.pages` — page file for the disk-only tree
- `bpt_hybrid.pages` — page file for the memory + disk tree

These output files may be overwritten by a later run. Keep a copy of the results you want to include in your submission.

## Design assumptions

- Each record has a unique alphanumeric key and a payload string.
- A node can hold up to **31 keys** before a split is required.
- Keys must be shorter than **32 bytes**, and payloads must be shorter than **128 bytes**, as required by the fixed-size record fields in the source.
- The node/page size is the value printed by the program. In the recorded full run, it was **5,400 bytes**; this is not the same as a standard 4 KiB disk page.
- The disk-only implementation uses a one-page cache, while the hybrid implementation uses a 256-page cache.
- Search timing is averaged over the successful searches performed by the benchmark (up to 10,000 keys).
- Disk I/O counters represent page reads and writes performed by the program. The operating system may also cache file data, which can affect elapsed time.
- The reported storage-size value is the program's estimate/measurement; it should not be treated as a complete measurement of total process RAM, including all allocator and runtime overhead.

## Results from my 10-million-record run

The following values are copied from the terminal output after running the program on 10,000,000 records. Actual times can differ on another machine or under different system conditions.

| Metric | Memory-only | Disk-only | Memory + Disk |
|---|---:|---:|---:|
| Insertion time | 33.597 s | 573.815 s | 491.811 s |
| Average search time | 3.465 µs/key | 30.626 µs/key | 24.454 µs/key |
| Tree pages/nodes | 4,820,269 | 482,069 | 482,069 |
| Reported storage size | 2,618,598,808 bytes (2,497.290 MiB) | 2,603,172,600 bytes (2,482.579 MiB) | 2,603,172,600 bytes (2,482.579 MiB) |
| Tree height | 6 | 6 | 6 |
| Disk page reads | 0 | 50,845,201 | 27,451,095 |
| Disk page writes | 0 | 10,964,096 | 10,931,391 |
| Cache hits | 0 | 157 | 23,394,263 |

### What I noticed

- The memory-only version was the fastest for insertion and search in this run.
- The disk-only version took the longest and recorded the most page reads.
- The hybrid version was faster than disk-only in both insertion and search. Its cache-hit count also shows that many page requests were served from the buffer pool.
- All three versions reported a tree height of 6.
